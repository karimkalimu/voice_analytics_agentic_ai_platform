# Project status — 2026-09-27

## Implemented

- FastAPI app in `app/main.py` with `GET /health` and startup SQLite initialization.
- `files` table in `app.db` with `id`, `user_id`, `upload_id`, `original_name`, `storage_path`, `status`, and `created_at`. `upload_id` is unique so a repeated completion hook does not duplicate a row.
- Firebase bearer-token verification in `app/auth.py`. `GET /files` returns rows for the verified UID only.
- `POST /hooks/tusd` in `app/routes/files.py`: `pre-create` verifies the token and metadata ownership; `post-finish` records the existing file with status `uploaded`. The reported path must resolve inside `storage/uploads/` and be a file, the final hook offset must equal its declared size, and the local file length must match. Other hook events are ignored.
- A newly registered completed upload schedules `app/transcription.py` in a FastAPI background task. The existing file is streamed to AssemblyAI, submitted with automatic language detection, and polled until completion or failure. Duplicate completion hooks do not schedule a second job.
- Completed English transcript text is stored once under the file owner's `storage/users/<uid-hash>/transcripts/` directory. Policy rejection uses `rejected`, a stable `rejection_code`, and a persistent user-facing `error`; API and processing errors use their existing failure statuses. Original and rejected audio is retained in the owner's directory.
- The `files` table now also has nullable `transcript_path`, `language`, and `error` columns. `GET /files` returns those fields plus a derived `transcript_available` boolean.
- A completed English transcript runs Layer 1 in the same background task. `app/llm.py` selects per-tier model, base URL, and key from `.env`; `app/analysis.py` uses the medium tier, sends a strict JSON schema, validates the response, and saves summary plus taxonomy JSON in SQLite. Transcript instructions are treated as untrusted data.
- `duration_sec` comes from local ffprobe inspection before transcription. The `files` table also has nullable `summary` and `taxonomy` fields. `GET /files` exposes `duration_sec`, `summary`, and the three taxonomy arrays.
- New nullable `audio_sha256`, `transcription_version`, and `analysis_version` fields support per-user reuse of language, duration, transcript, and unsupported-language results. A matching Layer 1 result is reused only with the same transcription and analysis versions; the analysis version incorporates prompt, schema, medium-tier model, and base URL. Failed results are retried on a new upload.
- Authenticated `GET /files/{id}` returns one owned file; `GET /files/{id}/transcript` returns `{"transcript": "..."}`; `DELETE /files/{id}` removes a terminal row and unreferenced local artifacts. Active rows return 409, and unowned or missing rows return 404.
- Startup resumes `uploaded`, `validating_audio`, `transcribing`, `validating_transcript`, `transcribed`, `analyzing`, and `analyzing_layer2` rows in one in-process background task. Completed and rejected rows stay terminal.
- Optional Layer 2 selections arrive in TUS `layer2_options` metadata as a Base64-encoded UTF-8 JSON array. The hook validates the allowlist on `pre-create` and `post-finish`; missing metadata selects no options. Layer 2 runs after Layer 1 and stores per-option results and versions in SQLite. FFmpeg computes normalized audio RMS; noun count, adjective count, sentiment, and topic mentions use the weak LLM tier. All prompts live in `prompts/*.md` and load at runtime.
- `analyzing_layer2` is recoverable after restart. `layer2_failed` is terminal but keeps the transcript, Layer 1 results, and any successful Layer 2 option results. Per-option cache keys cover audio hash, actual transcript digest for text options, prompt, schema, model, base URL, and configured Layer 2 version.
- Authenticated `POST /files/{id}/layer2` accepts a strict JSON `options` array and adds allowlisted options to an owned completed file with a readable transcript and Layer 1 output. It returns the same metadata as file details, with 202 for queued work or 200 when all requested results are current. SQLite `layer2_pending_options` tracks only the accepted request's unfinished options for restart recovery and is not exposed to Flutter. A failed retry retains prior successful results and versions.
- `GET /files` now accepts composable, validated date/time, duration, taxonomy-label, sentiment, RMS, noun-count, and adjective-count filters. Unknown, duplicate, malformed, and reversed parameters return 422. Filtering is applied only to the authenticated user's rows and uses fixed known fields.
- `count_nouns` accepts `unique_only`, a strict JSON boolean defaulting to `false`. Upload metadata uses a JSON object in `layer2_config`; later requests use the optional `config` object in `POST /files/{id}/layer2`. The normalized configuration contributes to the per-option cache version.
- `topic_mentions` requires `{"topic":"..."}` under its configuration. The topic is trimmed, limited to 1–100 characters, and included with the dedicated prompt, strict count schema, weak-tier model and base URL, and transcript digest in cache identity. Topic and transcript are separate untrusted values in the user-role JSON payload and are never interpolated into the trusted prompt.
- Completed audio and transcripts are physically partitioned under `storage/users/<sha256-of-Firebase-uid>/`. Active tusd uploads remain under `storage/uploads/`; completed data becomes a symlink there so tusd can still answer HEAD. Startup migrates legacy files and transcript paths. Filenames are validated and never used to build local paths.
- Layer 1 prompt and schema now require explicit evidence for technical, personal, and future-event labels, reject placeholder and duplicate labels, and leave absent categories as empty arrays. LLM refusals, invalid structured output, unsupported language, and processing failures save short user-facing reasons in `error`; internal details stay in server logs. AssemblyAI no-spoken-audio failures and completed empty transcripts are stored as `rejected` with `rejection_code: insufficient_speech` and a clear retry message.
- Pre-transcription guardrails use server-observed size, ffprobe stream/duration inspection, full ffmpeg decoding, and a conservative normalized RMS threshold. Post-transcription guardrails use English language detection, usable-word density, optional aggregate word confidence, deterministic profanity matching, and a strict weak-tier contextual profanity classifier.
- `GET /guardrails` exposes every configured threshold and seven string-only sections describing access, upload, audio, transcript, content, LLM-input, Layer 1, Layer 2, and failure protections without exposing prompts, policy terms, secrets, or exceptions. The `files` table stores `rejection_code` and `guardrail_version`; the version hashes thresholds, deterministic policy, guardrail prompt/schema, and weak-tier model configuration so cached transcripts always pass current validation before analysis.
- The completion hook transactionally limits each user to five active files by default. Excess completed uploads are registered as rejected with `active_limit_exceeded`, remain visible through the file APIs, and are not scheduled for processing.
- The `aggregate_jobs` table persists backend-controlled global or single-user scope, normalized request, `queued`/`running`/`completed`/`failed` status, structured result, safe error, and timestamps. Aggregate routes are not included in FastAPI; `python -m app.aggregate_job` and internal scheduling code create and run jobs without Firebase end-user authentication.
- Aggregate jobs use only eligible `completed` files with readable transcripts and valid Layer 1 data. They support optional user, inclusive time-range, and taxonomy filters plus allowlisted grouping by all files, user, taxonomy, or stored Layer 2 sentiment. User grouping partitions strictly by persisted `user_id` and synthesizes each user's summary, professional topics, personal topics, and upcoming events independently. User aggregate top-level results contain only global counts, duration, summary, grouping, and user groups; taxonomy is never merged across users at the top level. Global user jobs never send mixed-user content to an LLM. Global `all` is rejected; `all` requires an explicit user scope. Startup resumes queued or running jobs.
- `ubuntu_setup.sh` provides an idempotent Ubuntu 22.04/24.04 amd64 setup with Python 3.13, pip 25.0, exact versions for directly used Python packages, apt-installed FFmpeg/FFprobe, and checksum-verified tusd v2.10.1 under `.tools/`. `run_api.sh` and `run_tusd.sh` load `.env` and use repository-local executables.
- Local `.env` contains Firebase, AssemblyAI, and three LLM-tier credentials and settings, API host and port, and tusd upload and hook settings. `.env.example` documents the variables. `python-dotenv` loads `.env` when the app imports; the run commands also source it for service launch arguments.
- Service account JSON is present in the repository root and ignored by `.gitignore`. Its contents are not copied into code or documentation.
- This directory has no Git repository yet; `.gitignore` is ready if one is initialized later.
- The original assignment is archived at `docs/AI_full_stack_task.docx` and converted to `docs/AI_full_stack_task.md` for searching. Its instructions are background and do not expand the current backend-only stage.

## Scope and next changes

No signup/login, ORM, external queue, or Docker setup is present. Recovery resumes interrupted stages after a restart but does not resume an external AssemblyAI job ID; interrupted transcription starts again from the stored audio and may repeat an API call. Aggregate job recovery reruns jobs left queued or running. Recovery assumes one FastAPI process. Older rows with no stored processing version are not used as cache sources, since their configuration cannot be proven. The automated setup supports only Ubuntu 22.04 and 24.04 on amd64. Transitive Python versions and apt repository package revisions are not snapshot-pinned, and Python 3.13 is supplied by the third-party deadsnakes PPA. The full setup has not been executed on a native Ubuntu amd64 host from this macOS workspace.

The hook route currently checks that its direct caller is loopback because tusd and FastAPI run on the same machine. If a reverse proxy is added, keep `/hooks/tusd` private at the proxy too; a local proxy would otherwise appear to be a loopback caller.

tusd authenticates the initial upload POST through `pre-create`; it does not bind later PATCH or HEAD requests to the same Firebase user. Treat upload URLs as private if the POC is exposed beyond local testing.

For setup commands and the reason each component was chosen, see [README.md](README.md).
